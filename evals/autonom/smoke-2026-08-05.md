## Ambiguities and guesses

**1. `${CLAUDE_SKILL_DIR}` is not set in a Bash tool shell.** Every command in SKILL.md is written as `uv run ${CLAUDE_SKILL_DIR}/scripts/autonom.py …`. Echoing it in the run shell returned empty, so the commands as literally written would resolve to `uv run /scripts/autonom.py` and exit non-zero. I substituted the skill's real directory. Low severity if the variable is reliably populated in a normal main-session context, but nothing in the skill's own files says what to do when it is not, and a bare unset expansion fails in a way that looks like a broken script rather than a missing variable. A one-line fallback instruction would close it.

**2. How to derive the topic string.** `init` takes `"<topic>"`, and SKILL.md is precise about passing it *verbatim on resume* — but says nothing about how to compose it in the first place from what oiler asked for. The slug, the two artifact paths, the branch name, and every future resume all key on this string, so it is a consequential guess. I compressed the feature request into `add and list commands for timestamped notes`. A different reasonable compression yields a different slug and a different branch. Worth one sentence of guidance (e.g. "a short noun phrase naming the feature, not the full request").

**3. The onboarding question had no one to ask.** Startup steps 1 and 3 assume a human is present. In an automated run the mode and the repository confirmation both have to come from the invoking text. Inherent to clean-room testing rather than a skill defect, but it is worth noting that "confirm the run repository with oiler" is unsatisfiable in exactly the unattended context autonom targets.

**4. Whether a step-7 escalation stops the run immediately.** The forced guess. See *Defects found*, item 1.

**5. `git diff --stat 4c72b10 -- <path>` in the clean-review branch.** Not exercised (HEAD moved), but reading it cold: the command is written with one SHA and no second endpoint, i.e. base-vs-working-tree, which is what you want. It reads as a typo for a range on first pass. Not a defect — noting only that it invited a double-take.

## Defects found

**1. Contradiction: what a step-7 escalation blocks.** Two passages in `SKILL.md` give opposite instructions.

- *Startup step 6* (line ~133): "`escalated` is recorded *alongside* `complete`, so a step-7 escalation still leaves `next_step: 8` — a resume that trusts `next_step` alone **walks straight past an unresolved scope conflict and authors a plan against it.**" Authoring the plan is named as the harm. → stop at step 7.
- *Error handling*, the row step 7 explicitly routes to: "`escalations` exits `1` after either review | **Stop before `superpowers:subagent-driven-development`**, in both modes." SDD is step 10. → continue through steps 8 and 9, stop before implementation.
- *Ending* reinforces the second reading: "Print the artifact paths, the review diff ranges, and the escalation contents" — plural, presupposing both artifacts exist and both reviews ran.

These cannot both be followed. I took the first (stop immediately), because it names a concrete harm and because it is the conservative choice, but this was a coin-flip on textual authority, and the ambiguity is load-bearing: it decides whether a step-7 escalation costs one Fable dispatch or three. The fix is one clause in the Error handling row distinguishing the two gates — e.g. "a step-7 escalation stops before step 8; a step-9 escalation stops before SDD."

*Consequence for this run:* steps 8 and 9 (plan authoring, plan review, plan validator, second escalation gate) were not exercised. The plan validator's contract — in particular the fenced-marker trap described in *What the validators require* — remains untested by this pass.

**2. `${CLAUDE_SKILL_DIR}` has no documented fallback.** Detailed in *Ambiguities* item 1. Every one of the ten commands in the skill depends on it.

**3. No guidance on composing the topic string.** Detailed in *Ambiguities* item 2.

Nothing else in the run misbehaved. Specifically working as documented: `init`'s path derivation and `.gitignore` creation; the `resumed`/`next_step` payload; `status` on an empty repo returning `[]` and exit 0 rather than an error; both validators; the `prompt` subcommand's token substitution and leftover-token check; the two-command `rev-parse` / `ledger dispatched` split; the reviewer's `git -C` anchoring (the review commit landed in the run repository, not the session's); the reviewer's scope discipline (it edited four editorial findings in place and escalated the one that would change what gets built, exactly as its prompt asks); the escalation gate's exit-1-plus-print behavior; and the `complete`-then-`escalated` ledger ordering leaving `next_step: 8` and `last_status: escalated`.

The review commit is genuinely auditable: `git diff 4c72b10..f494325` is a nine-line insert, three-line delete, spec only. The separate-commit mitigation for granting a reviewer write authority did what it claims to do.
