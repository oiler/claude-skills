## 4. Ambiguities, gaps, and guesses

Twenty. Ordered roughly by how much damage the wrong guess would do.

**A1 — `${CLAUDE_SKILL_DIR}` is not set, and every command in SKILL.md depends on it.**
> `uv run ${CLAUDE_SKILL_DIR}/scripts/autonom.py status`

`echo "[${CLAUDE_SKILL_DIR}]"` in the Bash tool prints `[]`. As literally written, every command in the skill resolves to `uv run /scripts/autonom.py`. **Guessed:** substituted the absolute path `/Users/jrf1039/files/repo/claude-skills/autonom/scripts/autonom.py`. This is the single hardest breakage in the run — an agent that copy-pastes the documented command gets a file-not-found on the very first startup step, and the error (`uv` complaining about `/scripts/autonom.py`) does not point at the cause. If the variable is only substituted into prompt text and not into the shell environment, the commands need to be written as prose paths relative to the skill directory, not as shell variable expansions.

**A10 — `ledger 9 complete` vs `ledger 9 escalated` are in direct conflict, and only one of them advances the run.**
Step 9 says: `ledger 9 complete --slug <slug> --commit <review sha>`. The error table says: "`ledger <step> escalated`". Both apply when a review succeeds *and* escalates, which is exactly what happened. `autonom.py:_next_step` only counts lines matching `step (\d+) complete`, so an `escalated` line does not advance the resume point. Recording only `escalated` — the literal reading of the error table — leaves `next_step: 9` forever, and a post-compaction resume would re-dispatch a Fable reviewer over an already-reviewed plan and mint a duplicate review commit. That is precisely the harm the ledger exists to prevent, reintroduced by the escalation path. **Guessed:** wrote both lines, `complete` first (step 9's own ordering puts the ledger write before the escalations check), then `escalated`. The skill should say this outright, or `_next_step` should treat `escalated` as terminal.

**A6 — the plan validator enforces a template SKILL.md never shows you.**
> "Write the plan at the `plan` path from `init`, following `superpowers:writing-plans`"

`validate plan` hard-requires, outside code fences: the literal string `REQUIRED SUB-SKILL` co-occurring with `subagent-driven-development`; a heading matching `^## Global Constraints$` exactly; at least one `### Task N:` block; and per task, a `**Files:**` line and a `- [ ] **Step` checkbox. None of that appears in SKILL.md or in either reference file. A model that writes a competent plan in any other shape gets exit `1` with findings like "missing the '## Global Constraints' section" and no statement of what the section must contain. **Guessed:** read `writing-plans/SKILL.md` from the plugin cache for the template, then cross-checked `validate_plan()` in `autonom.py` for the exact literals. Both were necessary; the plugin doc alone does not tell you that the header must sit *outside* a fence, which `strip_code` makes load-bearing.

**A5 — "following `superpowers:brainstorming`'s spec conventions" has no safe execution path.**
Invoking that skill starts its Q&A checklist and its `<HARD-GATE>`, which autonom explicitly forbids ("autonom does not do discovery"). **Guessed:** read `brainstorming/SKILL.md` from the plugin cache without invoking it. SKILL.md should either name the required spec sections inline or say "read, do not invoke."

**A2 — the skill never says which repository the run happens in.**
`autonom.py` resolves the root from `git rev-parse --show-toplevel` of the *current working directory*, so cwd silently decides where every artifact and commit lands. SKILL.md says "Never construct an artifact path" but never says "the run is the repo you are cd'd into." Compounding it, dispatched subagents do not inherit the orchestrator's cwd. **Guessed:** ran every command with cwd set to the worktree, and verified after each review that HEAD moved *in the worktree*.

**A3 — step 3 creates the worktree before step 4 mints the slug.**
The worktree must exist before `init` runs, but the branch name is unspecified and the slug — the one canonical name for the run — does not exist yet. **Guessed:** hand-applied `slugify()`'s rules to predict `a-cli-that-converts-a-csv-file-to-json` and used it as the branch name. Either the steps should swap, or SKILL.md should name the branch convention.

**A4 — `using-git-worktrees` step 1a prefers a native tool that is bound to the wrong repository.**
That skill says to prefer `EnterWorktree` over `git worktree add`. `EnterWorktree` operates on the session's repo (here, `claude-skills`) and defaults to branching from `origin/<default-branch>`, which the temp repo does not have. **Guessed:** treated the native tool as unavailable *for this repository* and fell back to 1b. autonom inherits this whenever the run repo is not the session repo, and says nothing about it.

**A13 — checkpoint ending and escalation ending collide with no precedence rule.**
The *Ending* section says checkpoint prints paths + diff ranges + resume instruction. The error table says an escalation prints the escalation contents and hands over the decision. Both fired. Nothing says whether the resume instruction should still be printed when an escalation is outstanding — arguably it should not, since resuming into SDD is the thing being blocked. **Guessed:** printed both, with the escalation framed as blocking.

**A15 — the pre-dispatch HEAD has nowhere to live.**
> "Record `git rev-parse HEAD` before dispatching"

There is no ledger command for it and no file to put it in. If the session compacts during a multi-minute Fable dispatch, the before-SHA is gone and the review diff range is unrecoverable from the ledger alone. **Guessed:** held it in context. It survived, and the log made it recoverable anyway, but that is luck, not design — and the skill's own compaction story ("`autonom.py status` prints the resume point") does not cover it.

**A12 — "non-empty" is not defined for `escalations.md`.**
A reviewer that creates the file with a `# Escalations` heading and no findings produces a non-empty file and halts the run. Neither reviewer prompt says "create this file only if you have something to escalate" — they say "append the finding to…", which implies it without stating it. **Not exercised:** my escalation was substantive. A stricter rule ("non-empty after stripping headings and whitespace") would be cheap.

**A7 — the onboarding question conflicts with the resume offer.**
> "Ask it once, immediately, and do not ask anything else."

But step 1 says to "offer to resume" a matching incomplete run, which is a second question that must come first. **Guessed:** the resume offer is exempt from "do not ask anything else." Not exercised — `status` returned `[]`.

**A14 — the escalations file is never sectioned by review pass.**
Both reviews append to the same file, and the script never writes a separator or a header. If both passes escalate, the checkpoint prints a merged blob with no marker for which reviewer said what. The Fable reviewer happened to write its own dated `##` heading; nothing required it to.

**A18 — `init` dirties the tree and nobody cleans it up.**
`ensure_gitignored()` appends `.superpowers/` to `.gitignore` and never commits it. `git status --short` shows ` M .gitignore` for the entire run and at the checkpoint. In auto mode, SDD inherits a dirty working tree it did not create. SKILL.md never mentions the file is touched. **Guessed:** left it dirty, since the skill's `git add` lines name only the artifact.

**A16 — "a changed HEAD is the review commit" assumes exactly one new commit.**
The prompt tells the reviewer to "commit your changes alone" and not to touch HEAD or branch state, but nothing enforces it. If a reviewer made two commits, the recorded `--commit` would be right but the diff range would silently swallow the extra one. **Guessed:** trusted it, then verified with `git log --oneline` that exactly one commit appeared per dispatch. SKILL.md should prescribe that check; it costs one command.

**A8 — `<sha>` in the ledger lines is never sourced.**
> `uv run $A ledger 6 complete --slug <slug> --commit <sha>`

The step-7 text explains how to obtain a *review* SHA in detail, but steps 6 and 8 just say `<sha>`. **Guessed:** `git rev-parse HEAD` immediately after each authoring commit.

**A9 — commit messages use the raw slug, which reads badly.**
`docs: <slug> design spec` yields `docs: a-cli-that-converts-a-csv-file-to-json design spec`. **Guessed:** used the slug literally, since the table is explicit. Worth deciding whether the message should use the topic instead — the slug is machine-shaped and the commit log is human-shaped.

**A17 — "Emit one short line at each step transition" doesn't say where.**
**Guessed:** assistant prose between tool calls, not a file write, not a ledger entry.

**A19 — the checkpoint's "resume instruction" has no prescribed wording.**
> "the instruction to resume into implementation by invoking `superpowers:subagent-driven-development` with the plan path"

**Guessed:** wrote it as a literal invocation line with the absolute plan path. For a skill that is otherwise emphatic about the script owning verbatim output, leaving the checkpoint's own text to the model is inconsistent.

**A20 — `validate` path form is unspecified.** `init` emits absolute paths; SKILL.md shows `"<spec path>"`. Both work. **Guessed:** relative, from the run root. Harmless, but it means the recorded command differs run to run.

## 5. Things that did not work as documented

**`${CLAUDE_SKILL_DIR}` (A1).** The only hard breakage. Every documented command fails as written.

**`allowed-tools` does not cover the workflow SKILL.md describes.** The frontmatter grants:

```
Bash(uv run *) Bash(git add *) Bash(git commit *) Bash(git diff *)
Bash(git rev-parse *) Bash(git log *) Read Write Edit Agent Skill
```

The skill's own steps require, and this list omits:

| Needed for | Command | Granted? |
|---|---|---|
| Step 3, via `using-git-worktrees` | `git worktree add`, `git branch --show-current`, `git check-ignore` | no |
| Step 3 isolation detection | `git rev-parse --git-common-dir` | yes (`git rev-parse *`) |
| Steps 7/9 escalations check | any way to test file existence — `ls`, `test -f`, Glob, LS | no |
| Verifying the review commit landed | `git status` | no |

The escalations gap is the substantive one. SKILL.md says "Absent or empty both mean continue — neither the script nor a clean review creates it, so 'no such file' is the ordinary case," but with these tools the ordinary case is not detectable: `Read` on a missing file errors rather than reporting absence, and there is no Glob, LS, or `Bash(ls *)`. I used `ls -la`, which the frontmatter does not permit. Either add `Bash(ls *)`/Glob, or give `autonom.py` an `escalations` subcommand that exits `0` for empty/absent and `1` for non-empty — which would also fix A12 by defining "non-empty" in code rather than in prose.

Separately, the `allowed-tools` value is a space-separated folded scalar rather than a comma-separated list. I did not verify which form the loader accepts and am not claiming it is wrong, only that it differs from the comma-separated form used elsewhere and is worth a deliberate check.

**Everything else behaved.** `init`, `status`, `ledger`, `prompt`, and `validate` all did exactly what SKILL.md says, including the collision guard, the `{{TOKEN}}` substitution, and every documented exit code. Both Fable dispatches succeeded on `subagent_type: "general-purpose"` with `model: "fable"`, both respected their write boundaries, and both committed with the prescribed message. No path in the skill was missing, no flag was rejected, and no exit code meant something other than the table says.

## 6. Things I had to get from `autonom.py` because SKILL.md did not carry them

Each of these is a place the skill sent me to the source.

1. **The spec validator's required sections.** `SPEC_SECTIONS` demands headings at level ≥ 2 matching `problem|goal`, `architecture|design`, `error`, and `test`, plus one level-1 title, and each matched section must be non-empty. SKILL.md says only "following `superpowers:brainstorming`'s spec conventions." A `## Overview` / `## Approach` / `## Risks` spec — perfectly reasonable — fails.
2. **The plan validator's required structure.** See A6. The literal strings and the exact `^## Global Constraints$` anchor are only in the source.
3. **The forbidden-marker vocabulary.** `PLACEHOLDER_RE` (`TBD|TODO|FIXME|XXX`, `<placeholder>`, `[fill in]`) and `OPEN_QUESTION_RE` (`**Open question`, `???`, `[?]`). I avoided all of them while writing because I had read the regexes. Without them you write the spec, get exit `1`, and burn the one permitted repair attempt on something the skill could have told you up front.
4. **The plan red-flag phrase list.** `"Similar to Task N"`, `"add appropriate error handling"`, `"add validation"`, `"handle edge cases"`, and a bare `"Write tests for the above"` line. `add validation` is a common, innocent phrase — it is a plausible thing to write in a legitimate plan and it fails the build.
5. **That `strip_code` blanks fenced blocks and inline code before every scan.** This is load-bearing in both directions: it is why a plan may *document* a forbidden phrase inside backticks, and it is why the mandatory `REQUIRED SUB-SKILL` header must sit *outside* a fence — including outside the ```` ```markdown ```` fence that `writing-plans/SKILL.md` shows the template in. Copying that template verbatim produces a plan that fails validation. Nothing outside the source says so.
6. **That `init` writes to `.gitignore`.** (A18.)
7. **That `init` requires the superpowers plugin under `~/.claude/plugins/cache` and exits `2` without it.** SKILL.md's exit table says `2` covers "missing dependency" but never names this as a precondition, so a machine without the plugin fails at the fourth startup step with no forewarning.
8. **That `_next_step` counts only `step N complete`.** Directly determines A10. `failed` and `escalated` are inert to the resume logic — a run marked `failed` resumes as though nothing happened.
9. **That the run root is cwd's git toplevel.** (A2.)
10. **That `status` prints `[]` when there are no runs.** SKILL.md says it "prints every run directory and its resume point as JSON." Knowing the empty result is a JSON array, not `{}` or empty output, matters when you branch on it.
11. **That `prompt` requires `init` to have run first** (it checks for `progress.md` and exits `2`). Implied by step ordering, never stated.

Items 1–5 are the expensive ones. They are the difference between authoring an artifact that validates on the first attempt and burning the skill's single no-loop repair attempt learning the schema by trial. The determinism argument in SKILL.md — "Prose is yours, structure is the script's" — is sound, but the script currently owns a structure it never publishes. Either SKILL.md needs a validator-contract section, or `autonom.py` needs a `template {spec|plan}` subcommand that emits the required skeleton, which would fit the skill's own stated philosophy better than prose would.
