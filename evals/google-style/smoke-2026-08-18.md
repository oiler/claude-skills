## Ambiguities and guesses

### 1. A clean run certifies far less than the ten always-loaded rules

`SKILL.md` lists ten rules that apply to every sentence, then says the checker "gates the mechanically verifiable rules." Four of the ten have no gating rule behind them, and two of those have no rule at all:

| Always-loaded rule | Checker coverage |
|---|---|
| 2. Active voice with a named actor | `passive`, warning only |
| 3. Present tense | none among the 31 rules |
| 7. Code font for code and file names, bold for UI | none |
| 9. Conditions before instructions | `condition-order`, warning only |
| 10. Global audience, no directional language | none — no rule matches `above` or `below` |

Rule 10 is the sharpest case. The skill states it twice more, in `formatting-and-structure.md` and `code-and-ui.md`, and nothing enforces it. I self-enforced it by rewriting two sentences that pointed at the preceding code block. A writer who trusts the exit code gets no signal there at all. The skill should say which of the ten are gated and which are on the author's honor, because "run the checker until it exits 0" reads as the completion condition for the whole list.

### 2. `--list-rules` severity contradicts what the checker emits

`applying-to-artifacts.md` says: "`--list-rules` prints every rule with its severity and its source page; read it before you name a rule in prose, because the severity is part of what naming the rule claims." `--list-rules` prints `em-dash` as `error`. A spaced em dash emits a warning:

```text
emdash.md:3:22  warning em-dash  spaces around an em dash → Close the spaces: word—word. Reported as a warning because oiler's house style spaces em dashes and CLAUDE.md outranks this skill.

0 error(s), 1 warning(s)
EXIT=0
```

So a rule can emit both severities while `--list-rules` shows one. Following the reference's instruction literally would have made me call `em-dash` an error rule in prose, which is wrong for the case that actually fires most often in this house style. The same trap probably applies to `latin`, which the reference describes as splitting error and warning across `i.e.`, `e.g.`, `etc.`, `via`, and `vs.` while `--list-rules` prints one severity.

### 3. No per-artifact note exists for a guide or tutorial

`applying-to-artifacts.md` routes `README, API doc, guide, tutorial, reference` to this skill in one table row, then gives per-artifact notes for a spec, an implementation plan, a README, a PR description, a changelog, and a chat reply. A setup guide, which is what the task asked for, has no entry. I generalized from the README note, since a setup guide and a README share the install-and-run audience. That was a guess. The per-artifact notes are the most operationally useful part of the file, and the artifact type this task named is missing from them.

### 4. Code-block scope is undocumented

Nothing in `SKILL.md` or the four references I read states whether the checker inspects fenced code blocks. That matters: my troubleshooting section shows a sample CSV row containing a date, and `date-format` is an error rule that reports numeric dates. `formatting-and-structure.md` says a fictional example should use a day past the twelfth so the day cannot be read as a month, but that guidance is about ISO 8601 dates in prose, and I could not tell whether a date inside a sample data row is in scope at all. I hedged twice, writing `2026-03-19` in ISO form with a day past the twelfth, and moved on. The skill directory contains a `fenced_code` fixture, so the scripts define the behavior; the prose never states it. A single sentence in the "Run the checker" section would remove the guess.

### 5. `tally` in a heading: code font versus the heading rule

`code-and-ui.md` says a command-line utility name takes code font, and that the project or product of the same name does not. `formatting-and-structure.md` says a code item in a heading needs a descriptive noun next to it. My tool and my product share one name, `tally`, so both rules point at the same token and pull opposite ways. I wrote `tally` in code font throughout the body and bare in every heading, which leaves the same term formatted two ways in one document. The checker has no opinion. The skill gives no rule for a single-word tool whose name is also the product name, which is the normal shape of a CLI doc.

### 6. Reference selection is topic-indexed, artifact-blind

"Load only the files the current task needs. Loading all nine defeats the point of the split." The routing table is indexed by topic, which requires knowing what topics the finished document contains before writing it. I chose four references by guessing at the finished shape. The `word-list.md` row is worse: its trigger is "a word the checker flagged, or a term you are unsure of," which is purely reactive. My first run was clean, so I never opened it, and `voice-and-tone.md` states outright that the `excessive-claims` rule is narrower than the guide page behind it. A clean run therefore does not mean the prose complies with the word list. The skill does not say so, and the reactive trigger guarantees that a first-pass-clean document never gets checked against it.

### 7. Flag documentation is split across two files

`SKILL.md` documents three invocations and never mentions `--strict`, `--only`, or `--skip`. Those appear only in `applying-to-artifacts.md`, which a writer following `SKILL.md`'s reference routing loads for ownership questions, not for checker usage. `--strict` in particular changes the exit-code contract, and it is absent from the section titled "Run the checker."

### 8. Clean-room caveat on `CLAUDE.md`

`SKILL.md` says oiler's `CLAUDE.md` outranks the skill and then restates its operative rules inline, so I did not need to read it. Disclosure for the record: this session's auto-loaded context already contained global and project `CLAUDE.md` content. I read no file under the workshop directory and no file outside the skill directory. The inline restatement is a genuine design strength for clean-room use, with the standing cost that the skill hard-codes a summary of an external file that can drift.

### 9. `excessive-claims` matches an adverb without checking what it modifies

Running the checker on this report raised an `excessive-claims` error on a draft sentence in item 4, which said that the scripts define the fenced-code behavior in an unmistakable way, using the adverb the rule matches. The adverb modified the scripts, not the reader, so the rule's own rationale, "what is easy for the writer is not always easy for the reader," did not apply. `voice-and-tone.md` already records that the rule is narrower than the guide page it cites; this is the opposite edge of the same problem, where the rule matches a word without regard for what it attaches to. Per step 3 of the loop, I reworded until the pattern stopped matching rather than reaching for `--skip`.

Two follow-on observations. A gating rule produced a false positive on the first document long enough to contain one, which is a poor ratio for an error-severity rule. And the checker cannot be run over a document that quotes the words it matches: naming a flagged word in prose, which `applying-to-artifacts.md` explicitly tells you to do, re-triggers the rule. Writing this section required avoiding the vocabulary the section is about. The skill has no guidance for a document whose subject is the rules.
