## Ambiguities and guesses

**A1 — `${CLAUDE_SKILL_DIR}` is unset outside the harness, with no fallback documented.** Both `SKILL.md:48` and `structure-and-scaffolding.md:12` present the scaffolder command with a bare `${CLAUDE_SKILL_DIR}` and no note that it is an injected value. Copy-pasted into a plain shell it expands to `uv run /scripts/scaffold_plugin.py` and fails with a confusing "file not found." **Guessed:** substituted the absolute path to the skill directory.

**A2 — `--dir` semantics are never stated plainly.** The flag is shown as `--dir /path/to/plugins` and `--dir wp-content/plugins`; the overrides table documents `--namespace` and `--text-domain` but not `--dir` at all. That it is a *parent* directory (the plugin folder is created inside as `<dir>/<slug>`) is only inferable from the refuse-to-overwrite sentence. The task named a target of `.../clean-room/field-notes`, so I had to decide whether to pass that path or its parent. **Guessed:** parent. Correct — the tree landed where the task wanted it.

**A3 — Procedural vs. OOP: the two references model incompatible code shapes and nothing reconciles them.** This was the largest guess of the run. `admin-ui.md` writes everything as top-level `add_action()` calls with anonymous closures and `__NAMESPACE__ . '\\sanitize_options'` string callables — a procedural, single-file shape. `structure-and-scaffolding.md` prescribes the opposite: OOP + PSR-4, "one class per concern," an explicit `src/Settings.php` in its layout diagram, and a singleton whose `register_hooks()` owns all hook wiring. A developer following Build mode and Admin UI mode together — which the mode table explicitly tells you to do for "Add feature" — gets two mutually exclusive templates with no arbitration. **Guessed:** class-based, static `[ self::class, 'method' ]` callables, registered from `Plugin::register_hooks()`. Both shapes are defensible; the skill expresses no preference at the point where the two modes meet.

**A4 — "First write" is never located in the plugin lifecycle.** `admin-ui.md:133` and `vip-performance.md:67` both say to set autoload "where the row is written" / "on creation," but neither says *where in a scaffolded plugin that is*. The only hint is the scaffolder's `activate()` TODO comment ("set default options"). **Guessed:** `Plugin::activate()` via `Settings::install()`. This is very likely the intent, but it is inferred from a TODO comment in generated code rather than stated in prose — and it has a real edge case the skill never addresses (see D3).

**A5 — Option-name convention conflicts between the scaffolder and the reference.** The emitted `uninstall.php` suggests `delete_option( 'field-notes_settings' )` — kebab slug, `_settings` suffix. `admin-ui.md` prescribes `my_plugin_options` — underscore prefix, `_options` suffix. They disagree on both the separator and the suffix. **Guessed:** followed `admin-ui.md` (also what the task named), and updated `uninstall.php` to match.

**A6 — `meta_value` vs `meta_value_num` for "Location."** `admin-ui.md:83` gives the rule ("`meta_value_num` for numeric meta") but the choice still requires knowing the data's type, which the task did not state. **Guessed:** `meta_value`, treating a location as a string. Low risk; the rule as written was sufficient to decide.

**A7 — `WordPress-Docs` is enabled but no reference sample carries a docblock.** `vip-standards.md:85` names the ruleset and says it enforces docblocks, but every code sample in `admin-ui.md`, `security.md`, and `vip-performance.md` is a bare closure with no docblock at all. Transcribing them into `src/` as the layout requires produces `Missing doc comment` errors on the first `composer lint`. I wrote docblocks from scratch and still tripped a sniff the skill never mentions (capital-letter long descriptions). Not a blocker — the error message is self-explanatory and it is one `composer lint` cycle — but the reference code is not paste-ready under the skill's own ruleset.

## Defects found

**D1 — The scaffolder emits a `phpcs.xml.dist` using PHPCS array syntax deprecated since 3.3.0 and slated for removal in PHPCS 4.0.** Every `composer lint` on a *fresh, unmodified* scaffold prints:

```
DEPRECATED: Passing an array of values to a property using a comma-separated string
was deprecated in PHP_CodeSniffer 3.3.0. Support will be removed in PHPCS 4.0.0.
The deprecated syntax was used for property "text_domain" for sniff "WordPress.WP.I18n".
Pass array values via <element [key="..." ]value="..."> nodes instead.
```

...and the same again for `prefixes` on `WordPress.NamingConventions.PrefixAllGlobals`. Exit code is still 0, so it does not block, but the skill's flagship deterministic artifact ships noise on every single lint run and is on a removal path. `vip-standards.md:65-76` reproduces the identical deprecated syntax verbatim, so fixing the scaffolder alone would leave the reference stale. Fix is mechanical:

```xml
<property name="prefixes" type="array">
    <element value="Field_Notes"/>
</property>
```

This is the most concrete, most reproducible defect in the run — it fires on `composer lint` before a developer writes a single line.

**D2 — Four capability areas advertised in the description have zero content anywhere in the skill.** `SKILL.md`'s description is the routing contract, and it promises triggers for `register post type or taxonomy`, `enqueue scripts/styles`, `shortcodes`, and `multisite or network-activated plugin`. Grepping all seven reference files:

| Advertised trigger | Coverage |
|---|---|
| `register post type or taxonomy` | Zero. `register_post_type` / `register_taxonomy` appear nowhere. Only passing prose mentions of "custom post types" while discussing `flush_rewrite_rules()`. |
| `enqueue scripts/styles` | Zero. `wp_enqueue_script` / `wp_enqueue_style` appear nowhere. The layout diagram lists an `Enqueues.php` file it never explains. |
| `shortcodes` | Zero. `add_shortcode` appears nowhere. |
| `multisite or network-activated plugin` | Zero actionable guidance. Two incidental prose mentions (`audit-checklist.md:156`, `documentation.md:187`), neither about writing multisite-aware plugin code. |

This bears directly on this task: the column feature targets a `note` CPT, and I had to assume it was registered elsewhere because the skill offers nothing on registering one. Had the task said "register the CPT too," Build mode would have routed me to `structure-and-scaffolding.md` and left me with no guidance. The mode table's "Add feature" row says to read "the relevant deep reference below" — for these four topics, no such reference exists. An over-promising description is exactly the failure mode of over-triggering into a skill that then cannot answer.

**D3 — `add_option()` in `activate()` is single-site only, and the skill claims multisite in its description.** Following A4's inference, the option row is created in `Plugin::activate()`. On a network-activated multisite plugin, `register_activation_hook` fires once for the network, so `add_option()` writes to the activating site's `wp_options` and every other site in the network silently gets no row — the exact class of bug the skill's own `documentation.md:187` uses as a changelog example ("settings not saving on multisite"). Because the description advertises multisite, the skill should either say how to handle it (`get_sites()` + `switch_to_blog()` loop, or lazy creation on first read) or say plainly that it does not cover multisite. Currently it does neither. Downstream of D2 but a distinct, concrete failure.

**D4 — `phpcs.xml.dist` sets `text_domain` twice, once via a mechanism that does nothing.** The emitted file has both `<config name="text_domain" value="field-notes"/>` (line 19) and a `WordPress.WP.I18n` `<property name="text_domain" .../>` (lines 26-30). `<config>` directives set PHPCS CLI config values, not sniff properties; the `<config>` form is inert for this sniff. Only the property line has effect — and it is the one throwing the D1 deprecation. Cosmetic, but it makes the emitted ruleset look like it has a redundancy when it actually has one working line and one dead one. `vip-standards.md:56-69` documents the same duplication as intended output.

**D5 (low) — the `${CLAUDE_SKILL_DIR}` invocation is undocumented.** Restating A1 as a defect: the variable appears in the two most prominent commands in the skill with no note that it is harness-injected and no fallback. One sentence fixes it.

## Verdict rationale

**Pass.**

Every step of the workflow completed as the skill's files describe, and the hard gate was met: `composer install`, `composer lint`, and `composer test` all exit 0 in the plugin directory, verified sequentially in a final clean run (`OK (4 tests, 8 assertions)`).

The load-bearing evidence for "as documented," not merely "it worked":

- The scaffolder's determinism claims held under test — derivations (`field-notes`, `Field_Notes`) matched the documented rules exactly, the emitted tree matched the documented layout file-for-file, and the refuse-to-overwrite guarantee was verified directly (exit 1, no partial writes).
- The fresh-scaffold claim held: `composer install && composer test` passed before I touched anything.
- `admin-ui.md`'s traps are real and its warnings are actionable. The `edit-` screen-id prefix, the absent `autoload` key on `register_setting()`, the `add_option(..., '', false)` fourth-argument pattern, and the `is_admin()` / `is_main_query()` guard were all specific enough to implement without a second source, and the autoload pattern lints clean under the ruleset the skill ships — the one place a plausible contradiction could have appeared and did not.
- `structure-and-scaffolding.md`'s test-harness prose was unusually accurate. Its two non-obvious warnings — the singleton records hooks once per process, and `wp_stub_reset()` in `setUp()` would wipe that recording — both described the observed behavior precisely, and my added hook-registration tests passed on the first attempt because of them.
- Only one lint error was introduced across ~300 lines of new PHP, and it was a docblock-style sniff, not a substantive violation.

The findings are ambiguities and coverage gaps, not blocked steps. Weighing them:

**D1 is the one I would fix first** — it is the only defect that fires on a fresh scaffold with no user code, it hits every lint run, and it is on a removal path in PHPCS 4.0. The fix must land in both the scaffolder and `vip-standards.md`, which reproduces the deprecated syntax verbatim.

**D2 is the largest defect by scope** and the one most likely to cause a bad outcome in the field. Four advertised trigger areas with zero content is a description-scope failure: the description over-promises, the skill triggers, and then the references have nothing. It did not block this task only because the task supplied a CPT rather than asking me to register one. The fix is a judgment call — either write the missing sections or narrow the description — but the current state should not persist, since a pushy description that triggers into an empty reference set is worse than not triggering.

**A3 is the finding most likely to produce inconsistent output across runs.** The procedural/OOP split between `admin-ui.md` and `structure-and-scaffolding.md` is a genuine contradiction at the exact seam the mode table tells you to work across, and nothing arbitrates it. Two competent runs of this same task would plausibly produce structurally different plugins. For a skill whose stated value is deterministic, opinionated output, that is worth one explicit sentence in `admin-ui.md` saying which shape wins inside a scaffolded plugin.

None of these prevented the documented workflow from running end to end, which is what the verdict turns on.
