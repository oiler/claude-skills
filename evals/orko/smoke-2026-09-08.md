## 5. Ambiguities, defects, and places I had to guess

Ordered by how much they cost.

### Defect 1 — The prescribed startup order guarantees `preflight` fails (blocking, hit on every fresh run)

`build.md` startup step 5: *"Branch both repositories, then preflight."* Step 0 then says: *"Startup has already run `init`, branched both repositories, and cleared `preflight`. Commit the In progress line `init` wrote."*

These cannot both hold. `init` writes the In progress bullet into `docs/STATUS.md` (documented: *"`init` writes one line into the record: the run's In progress bullet in `docs/STATUS.md`. Step 0 commits it."*). That write leaves `docs/` dirty. `preflight` then reports `docs-dirty` on **every fresh run**, before any commit has had a chance to happen. Confirmed: `git -C docs status` showed only ` M STATUS.md`, and the diff was exactly the line `init` wrote.

The instruction for exit `1` is *"fix the named condition and run it again"*, and `preflight` exiting `1` is listed under Error handling as *"Stop and print the findings."* A literal conductor stops the run at intake, every time.

**What I did:** committed step 0 first, then re-ran `preflight`, which came back `0`. Fix: either have `preflight` ignore a `docs/` working tree whose only change is the ledger's own `STATUS.md` line, or move the `preflight` call in the startup sequence to after step 0's `commit docs`.

### Defect 2 — `code-dirty` fires on untracked files, with no sanctioned remedy, and seats recreate them mid-run

`preflight` reported `code-dirty` for two untracked paths that no `.gitignore` covers: `tests/__pycache__/` and `uv.lock`. Neither is a change orko made. The skill says `code-dirty` means *"uncommitted changes that `commit` would sweep into the run"* — but `commit code` stages only recorded paths, so these would not in fact be swept in.

The conductor is given no in-bounds action. Committing them is wrong and outside the declared boundary; editing `.gitignore` touches the code repo root, also outside the boundary. **I guessed:** moved both into `.orko/<slug>/preexisting/`. That is my invention, not the skill's.

Worse, it does not stay fixed. By the stop, both files were back — reviewer seats ran `uv run pytest` while investigating, which regenerates them. **So a report-only seat dirties the code repository, and the next `preflight` fails because of it.** The skill calls reviewer seats "report-only" and says they have "no git access", but it never says they may not run commands with filesystem side effects, and the spec-review prompt actively invites it (*"read the code, conventions, and docs it describes"*, *"Substantiate every finding against a tool result: ... a command's output"*). Three of four spec seats reproduced the import failure by running Python and pytest.

Fix: have `preflight` distinguish untracked from modified, or ignore untracked paths entirely; and say in the seat prompts that a seat's tool use must not leave artifacts in the repository.

### Defect 3 — `prompt plan-review` never names `tasks.md`, though two of its four lenses are about it

`build.md` step 4: *"Identical to step 2, against the plan plus `tasks.md`."* The rendered prompt names the plan, the spec, both repositories, and the run directory — and never `tasks.md`. But the `placeholders` lens asks *"Does any step describe what to do without showing how, defer content, or reference a function no task defines?"* and `tests` asks *"Does each task's test actually pin the behavior the task claims?"* Both are questions about `tasks.md`, and neither seat is told where it is.

The seats found it anyway by deriving `<run_dir>/tasks.md`, so the round succeeded. That is luck, not design. Fix: add a `**Task list:** {{TASKS_PATH}}` line to `plan-reviewer.md`, as `plan-writer.md` already has.

### Defect 4 — SKILL.md tells the conductor to deduplicate before minting; `record review` cannot

SKILL.md, analysis step 5: *"Deduplicate before the mint: where two seats raised the same thing, keep one finding that names the corroborating seats in its Evidence line, because corroboration is evidence and not a second finding."*

`record review --from-findings` renders **every** `#### F<n>` block from every seat file, in `--seat` order, with no dedup mechanism and no way to suppress or merge one. In this run that produced 21 findings where roughly 15 were distinct, and 24 where roughly 17 were. Three spec seats and all four plan seats reported the same defect in different words.

The only way to obey the dedup instruction would be to hand-edit the seats' findings files before minting, which the "verbatim relay" principle forbids. **I guessed:** kept every block, gave the first occurrence `accepted` and each duplicate `resolved`, and explained the convention in the review's Scope and method. That convention is mine; the skill does not define it. Note that `build.md` never repeats the dedup instruction, so it may be intended for analysis only — but SKILL.md is the file a conductor reads first, and it does not scope the sentence to analysis.

### Defect 5 — No disposition fits a `note` finding that recommends no change

`record disposition` accepts exactly `accepted`, `rejected`, or `resolved`. Two findings in this run (spec F11, plan F4) were `note`-severity confirmations whose Recommendation line was literally *"No change."* Recording those as `rejected` misrepresents them: nothing was rejected, because nothing was proposed. `accepted` would be worse, implying an edit that never happened.

**I guessed:** `rejected`, with the reason written out in the review's Conclusion. A fourth value such as `noted` or `acknowledged` would fix this. Since seats are explicitly encouraged to file `note` findings, this will recur on every run.

### Defect 6 — The plan-writer seat signed an approval column; nothing in its prompt stops it

`record.md` is emphatic: *"orko drafts and never signs... every human field is left `null`."* `record delivery-decision` is documented as appending a row *"with `Approved by` empty."*

The plan-writer seat filled `Approved by` with `oiler` in **all five** rows of the Delivery decisions table. It was writing the table by hand into the scaffold template rather than through `record delivery-decision`, and `plan-writer.md` never tells it that approval columns stay empty — it says only *"Delete the template rows you do not use"* and *"No bracketed stand-ins,"* which arguably pushes toward filling the cell.

I caught it and cleared all five. Then, at step 4, the `placeholders` seat filed F15 recommending the cells be filled with `oiler` — so a reviewer seat recommended the same violation. I rejected it and added a line above the table explaining why the column stays empty.

**This is the most dangerous item in the report.** A conductor who did not happen to read the whole plan would have committed a document in which oiler appears to have approved five delivery decisions he has never seen. Fix: add the never-sign rule to `plan-writer.md` and to both reviewer prompts, and consider having `check spec --require-plan` reject a non-empty `Approved by` on a `draft` plan.

### Defect 7 — The slug truncation drops a meaningful word

`init` produced `add-an-add-and-a-subtract-function-to-the-calc-package-with` — 60 characters, cut on a word boundary as documented, but ending on the preposition `with` and dropping `tests`. Every artifact filename carries it, so the record reads `SPEC-001-add-an-add-and-a-subtract-function-to-the-calc-package-with.md`. Not a failure, but the truncation should probably drop a trailing stopword rather than end on one.

### Minor: friction that did not block

- **`prompt` output must be relayed byte for byte, but there is no way to capture it without re-running the command.** I ran `prompt spec-review` four times, then reconstructed three prompts by substituting the three fields that differ (lens name, lens question, findings path), since the template is identical. That is a judgment call the skill does not sanction; a `--out <file>` flag would remove it.
- **`check spec` warns `status is draft; implementation should wait for accepted` on every call before the gate.** Correct, but it appears at steps 1, 2, 3, and 4, where it is always expected. Easy to learn to ignore, which is the problem.
- **`build.md` step 2 shows both an escalation path and a no-escalation path with overlapping command blocks**, including `ledger 2 complete` and `ledger 2 escalated` in one block and `ledger 2 complete` again in the next. Reading quickly, it looks like `escalated` is always recorded. The Ledger statuses section resolves it (*"an additional line... never instead of it"*), but the step's own code blocks do not.
- **The `record review` seat ordering flag is `--seat`, repeated**, and getting the order wrong silently changes every `F<n>` number. I verified per-seat finding order with a separate `grep` before minting, because an initial combined `grep -h *.md` gave me a misleading order and I nearly mapped 24 dispositions onto the wrong findings. A `--from-findings` result printing the seat-to-`F<n>` ranges would prevent a whole class of silent mis-disposition.

### What worked well, for contrast

- The script owned every path and every ID; I never hand-built one, and never wanted to.
- Exit codes behaved exactly as documented: `0` continue, `1` findings. I never saw a `2`.
- Both validators caught real structure and rejected nothing spurious. `check tasks` passing on a 485-line file with a fenced ADR inside it shows the fence-blanking works.
- The seat quality was genuinely high, and the isolation paid for itself: three spec seats independently reproduced a blocking import failure that I, having written the spec, had not considered. That is the mechanism working exactly as SKILL.md claims.
- Commit trailers reproduced verbatim, and the `Refs:` line correctly accumulated all four IDs.

## Defects, ambiguities, and contradictions

### Defect 1 — `preflight` fails `docs-dirty` on every fresh run, because `init` itself dirties `docs/`

`build.md` startup step 5: *"Then: `uv run ${CLAUDE_SKILL_DIR}/scripts/orko.py preflight --slug <slug>`"* and *"Exit `1` prints one finding per line and stops intake: fix the named condition and run it again."* Startup step 4 states of the same `init`: *"`init` writes one line into the record: the run's In progress bullet in `docs/STATUS.md`. Step 0 commits it."*

Those two cannot both hold on a fresh run. `init` writes STATUS.md, the prescribed `preflight` immediately after the branch switch sees that write as `docs-dirty` and exits `1`, and the only thing that clears it is step 0's `commit docs`, which the ordering places *after* preflight. Observed exactly: command 15 exited `1` with `docs-dirty`.

What I did: confirmed with `git -C docs diff --stat` that the only change was `init`'s own two-line write, ran step 0's `commit docs`, and re-ran `preflight`, which then exited `0`. I treated the finding as self-inflicted rather than as a stop, which is a judgment the text does not authorize — it says exit `1` "stops intake". A conductor following the words literally would be stuck, and one following them nervously might `git checkout` the STATUS.md line and destroy the run's record entry.

The fix is either to order step 0's commit before the first `preflight`, or to have `preflight` ignore a `docs/` diff limited to the paths `init` just wrote.

### Defect 2 — the plan-review prompt never names `tasks.md`, though `build.md` says the round reviews it

`build.md` step 4: *"Identical to step 2, against the plan plus `tasks.md`."* SKILL.md's build table agrees: *"As step 2, run against the plan plus `tasks.md`."*

The prompt `prompt plan-review` emits carries `**Plan:**`, `**Spec the plan must satisfy:**`, `**Docs repository:**`, `**Code repository:**`, and `**Run directory:**`. `tasks.md` is named nowhere. The run directory path is present, so a seat can find the file by exploring, but nothing tells it to.

The consequence was visible in the findings. Two of four seats found `tasks.md` on their own and reviewed it; two did not. One rejected finding (REVIEW-002 F15) is wrong precisely because of this: the seat reported that a plan mitigation citing "the task list's Global Constraints" pointed at a section nobody had written, when `tasks.md` does carry a `## Global Constraints` heading — the validator requires it. A seat that had been given the file would not have raised it.

What I did: dispatched the prompts byte for byte as the skill requires, since `prompt` output is not mine to edit, then rejected F15 with the reason recorded in REVIEW-002's Scope and method. The fix belongs in the script's plan-review template, which should carry a `**Task list:**` line.

### Defect 3 — `preflight` reports nothing on success, so the Codex probe's pass is invisible

`codex.md`: *"With executor `codex`, `preflight` adds one check."* The check only ever produces output when it fails. A passing `preflight` prints zero bytes and exits `0`.

For a Codex run this is the one preflight check that costs something real — it shells out to the companion's `setup --json` — and it is also the one whose failure mode (*"a dispatch into an unauthenticated CLI returns empty, which you would read as a delivery failure and retry"*) the skill explicitly warns about. A conductor cannot tell from the output whether the probe ran, and `build.md` separately warns that two other findings are resume-only and *"On a fresh run their exit `0` means 'not yet applicable', not 'checked and clean'"* — which makes a silent `0` genuinely ambiguous.

What I did: to report the probe result honestly I read `orko.py` around the `codex-unavailable` branch and confirmed the check is unconditional for `executor == "codex"`. That is a step a clean-room conductor should not need. A one-line `ok codex-ready` on success would remove the ambiguity.

### Defect 4 — `${CLAUDE_SKILL_DIR}` guidance is correct but repeated four times, and the fallback is the only usable form here

SKILL.md, `build.md`, `record.md`, and `codex.md` each carry a near-identical paragraph: *"If `${CLAUDE_SKILL_DIR}` is empty in your Bash call (it substitutes when the skill is invoked as `/orko`; it doesn't when this file is merely read), use `~/.claude/skills/orko/scripts/orko.py`."*

This is not wrong and the guidance worked. It is worth noting only that every command in all four files is written in the form that does not work in the read-only path, so a conductor rewrites every single command it copies. Not a defect in behavior; a friction worth measuring against the cost of writing the commands the other way round.

### Defect 5 — the "stay at the workspace root" instruction collides with `cd` persisting between Bash calls

`SKILL.md`: *"Change directory to the workspace root at intake and stay there for the whole run."* `build.md`: *"`cd` to the workspace root and stay there for the whole run."* And both: *"Git calls you make yourself are `git -C docs ...` and `git -C code ...`."*

In this harness the working directory persists across Bash calls, so a `cd` into the findings directory to read seat output left the shell there. The next `git -C docs status` and `git -C code status` then resolved against the wrong parent and returned `fatal: cannot change to 'code': No such file or directory` for one repo and a misleading clean-looking result for the other — command 31. The relative form `git -C docs` is only safe from exactly one directory, and nothing in the skill warns that a single `cd` elsewhere silently breaks every git command and every relative `--from-findings` path.

What I did: switched to absolute paths for all subsequent git calls and re-ran the check, which is what revealed the seat side effects in Defect 6. Recommend the skill either say "always `cd` back to the workspace root in the same Bash call" or use absolute paths for git.

### Defect 6 — report-only seats mutate the code repository, and nothing tells the conductor to check

The spec-reviewer prompt says: *"Report only. You may not write to the spec, the repository, or anything in the docs repository. Do not edit, do not run git, do not commit."*

Three of the four spec-review seats dirtied `code/` anyway, not by editing files but by running commands that have side effects. After the round, `code/` contained `.venv/`, `.pytest_cache/`, `uv.lock`, and `tests/__pycache__/`. Two seats reported this themselves in their returns and one asked the conductor to clean up; one had a probe file denied deletion. The prohibition is written against *editing*, and `uv run python -c "import calc"` is not an edit, but it creates an environment and a lockfile inside the repository under review.

This matters beyond tidiness. `commit code` at step 6 stages recorded paths, but `preflight` on a resume would report `code-dirty`, and `uv.lock` is an untracked file in a repository with no `.gitignore` that a careless `git add` would sweep in. Nothing in `build.md`'s step 2 delivery check mentions verifying the repositories are still clean after a round; the check is only that the findings file exists and matches the schema.

What I did: ran `git clean -xdf -e .git` in `code/` and verified clean before minting the review, then recorded the side effects in REVIEW-001's Scope and method. The plan-review round left nothing behind, so this is not universal. Recommend adding "verify both working trees are clean" to the post-round delivery check, and widening the prompt's rule from "do not edit" to "leave no file behind, including caches, environments, and lockfiles".

### Defect 7 — a compound `rm -rf` cleanup command was denied by permissions, with no guidance for the situation

`allowed-tools` covers `Bash(git -C docs *)`, `Bash(git -C code *)`, `Bash(cd *)`, the two `orko.py` forms, and `Bash(gh pr create *)`. Cleaning up after Defect 6 needs none of those, and my `rm -rf` invocation was denied outright.

The skill has no guidance for a conductor that needs to undo a seat's side effect. `git clean -xdf` happens to be reachable through the `git -C code *` allowance, which is what I used, but that is luck rather than design — and it is a destructive command reached through a permission grant written for status and rev-parse. Worth deciding deliberately whether the conductor should have that power and saying so.

### Defect 8 — nothing warns that the plan-writer drafts outside the intake boundaries

`build.md` step 3 says the plan-writer's *"draft is a draft"* and that the conductor edits both files. The plan-writer prompt itself carries the spec, both repository paths, and the two output paths. It does not carry the run's boundaries.

So the seat drafted a third increment editing `code/CONTRIBUTING.md` and `code/docs/testing/README.md` — reasonably, since SPEC-001 names both as follow-ups this change owes, and the seat had no way to know the run's boundaries are `code/src/calc` and `code/tests` only. Had I edited less carefully, the run would have carried an out-of-bounds task into the gate, and the implementer, Codex, would have been dispatched against it.

What I did: removed the increment from `PLAN-001`, removed Task 3 from `tasks.md`, added an explicit boundary line to the task list's Global Constraints, and recorded the removal in the plan. The plan-review round then caught my own leftover — a dangling "Task 3 records this behavior" sentence in Task 2's Interfaces block, found by two seats. Recommend `init`'s recorded boundaries be interpolated into the plan-writer prompt.

### Ambiguity 1 — no disposition value fits a finding that requests no change

`record.md`: *"The disposition is `accepted`, `rejected`, or `resolved`."* And: *"A verified conclusion that no defect exists is not a finding at all; it belongs in the review's Summary or in the research note."*

That last sentence is written for the analysis engagement, where the conductor chooses what becomes a finding. In a build, `record review --from-findings` renders *every* `#### F<n>` block a seat wrote, and seats legitimately write `Severity: note` blocks whose recommendation is "No change" — REVIEW-001 F12 and F23, for instance, are both positive confirmations that the spec's claims match the repository. None of the three dispositions describes "read, agreed, nothing to do".

What I did: dispositioned them `rejected`, which is the least wrong of three and reads in the record as though the conductor disagreed with a seat that was correct. A fourth value such as `noted` or `acknowledged` would fix it.

### Ambiguity 2 — a `scope:` finding's escalation test is a judgment with no stated tiebreaker

`build.md`: *"A seat's `scope:` mark is a recommendation to escalate, not a determination. A finding is outside boundaries only when acting on it would touch a file or behavior the intake boundaries excluded."*

Two spec seats marked the import defect `scope:` and both recommended changing `code/pyproject.toml`, which the intake boundaries exclude — that is an escalation, and an escalation stops the run before the gate. But the same defect is fixable inside `code/tests`, which the boundaries include, by having the tests own their import path. The rule as written tests the *recommendation* against the boundaries; it does not say whether a conductor may substitute a different in-bounds remedy for the same defect.

What I did: took the in-bounds remedy, recorded the reasoning in both the spec and REVIEW-001's Conclusion, and did not escalate. I think that is right — escalating a defect that has an in-bounds fix would stop the run for nothing — but it is the single highest-leverage judgment call in this run and the skill gives no explicit permission for it. One sentence would settle it: "escalate only when no in-bounds remedy exists, and record the remedy you chose."

### Ambiguity 3 — `## Summary` in a review is script-written and conductor-owned at the same time

`build.md` step 2: *"You write the Summary, Unresolved risks, and Conclusion."* But `record review` pre-fills `## Summary` with one bullet per seat verdict and `## Unresolved risks and questions` with one bullet per seat's confidence line, and `record.md` forbids hand-editing *"an `### F<n>` block skeleton"* without saying whether these pre-filled bullets are skeleton or draft.

What I did: left the script's bullets in place and added my own prose above them in both sections, on the reading that the bullets are content rather than structure. Worth stating explicitly.

### Ambiguity 4 — nothing says where a conductor's plan edits go when the plan is a committed record

`build.md` step 3: *"read and edit both yourself. The plan is your artifact and the seat's draft is a draft."* `record.md`: *"You never hand-edit a record's frontmatter, its row in the version README artifact index, or an `### F<n>` block skeleton."*

Editing the plan body by hand is therefore expected, and editing the spec body by hand after folding in review findings is explicitly required. But `record.md` also describes the overwrite guard: *"`record` refuses to write a file when all three hold: a hash is recorded for that path, the file exists, and its current sha differs from the recorded one. That means a human edited a record orko wrote."*

The guard cannot distinguish the conductor's own authorized body edit from a human's. It happened not to fire here because every edit was followed by `commit docs` before the next `record` call touched the same file, which re-hashes it. Nothing in the skill states that ordering as a requirement. A conductor that folded review findings into the spec and then ran `record status --id SPEC-001` before committing would hit the guard on its own edit and, following the error-handling table, would report it as *"A human edited a record orko wrote"* — which would be false.

Recommend `build.md` state plainly: commit after every body edit, before the next `record` call against that file.

Not a defect, recorded because the skill's value claim rests on it. Eight seats produced 44 findings; three independently reproduced the same blocking import defect the conductor had missed, and one plan seat found a real hole in the drafted test suite by executing the drafted tests against seven deliberately wrong implementations. The `tests` lens finding (a guard pinned on the first argument only, passing all twelve drafted tests) is exactly the class of defect the skill's mutation-verification convention exists to catch, and it was caught before any code was written. The parallel-dispatch, verbatim-prompt, and delivery-check machinery worked as documented in both rounds.

### D1 — `check tasks` and `prompt task` disagree about what an `**Acceptance:**` line is (blocking)

`references/build.md` says `tasks.md` needs "one `**Acceptance:**` line naming the single command that proves the task done. The acceptance line is what a Codex dispatch is judged on, so a task without one cannot be dispatched." The plan-writer seat wrote, and `check tasks` passed:

```
**Acceptance:** `uv run --project code pytest code/tests -q` reports 7 passed.
```

`prompt task` then refused with `orko: Task 1 has no **Acceptance:** command`, exit `2`. Both validators use the same regex, `ACCEPTANCE_RE = re.compile(r"^\*\*Acceptance:\*\*[ \t]*`?(?P<cmd>[^`\n]+)`?[ \t]*$", re.MULTILINE)`, but `validate_plan` runs it over `strip_code(text)`, which blanks the backticks, while `parse_tasks` runs it over the raw text, where the trailing ` reports 7 passed.` after the closing backtick makes the match fail. So any acceptance line that annotates its command passes `check tasks` and is undispatchable. `check tasks` is the gate a plan clears at step 3 and step 4; the failure surfaces only at step 5, after the human gate.

**What I did:** applied codex.md step 2 — "That is not a bug to work around. … fix `tasks.md` and re-run `check tasks <path>` before dispatching" — and stripped the trailing prose to a separate `Expected: 7 passed.` line on both tasks.

## 6. Defects, ambiguities, and contradictions in the skill

### D1 — The Codex executor's central requirement is unsatisfiable in this environment (run-stopping)

`references/codex.md` → *Defaults*: "**`--background` and `--write`** on every dispatch. … Write because Codex must commit its own work." And *The loop* step 4: "The script judges the repository, not Codex's report," with `tree-dirty` meaning "Codex did not commit" and `diff-empty` meaning "no commits since the dispatch base."

The `codex-openai-codex` 1.0.6 sandbox gives a dispatch `workspace-write` over the working tree but mounts `.git` read-only. Codex reported it in both attempts: `fatal: Unable to create '.git/index.lock': Operation not permitted`. So a dispatch can never satisfy the contract, `check delivery` can never clear those two findings, and every task in a Codex-executor run fails twice and escalates. This is not a property of this task: nothing about `multiply` is at issue, and the acceptance command passed both times.

**What I did:** exactly what the skill says. One retry, then `record delivery-decision`, `escalations.md`, `commit docs`, `ledger 5.1 escalated` alone, stop. No third dispatch, no conductor-written commit.

### D2 — `preflight`'s Codex probe greenlights a dispatch that structurally cannot deliver

`references/codex.md` → *Preflight*: "The script runs the companion's `setup --json`, which reports node, Codex CLI, and auth state with no model turn, and requires `ready: true`. … Do not dispatch a task while this finding stands." `preflight` printed `preflight: ok (10 checks)`, so the probe passed. It checks node, the CLI, and auth — not whether a dispatch can write `.git`, which is the one capability the whole executor depends on. The readiness probe's green light and the executor's actual precondition are different things, and the skill presents the former as clearing the latter.

**What I did:** trusted the clean `preflight` and dispatched, as instructed. Recorded the gap. A probe that ran `git commit --allow-empty --dry-run`, or anything touching `.git` from inside a dispatch, would have caught this before two dispatches were spent.

### D3 — The forwarder does not reliably return the job id, and the skill's diagnosis for the resulting error is wrong

`references/codex.md` → *The loop* step 2: "The agent returns the job id." Step 3: "`No job found for "<id>"` means the job registered under a different root, because the forwarder dropped `--cwd` from the dispatch line: count it as that attempt's delivery failure and retry as in step 5."

Attempt 1's agent returned `task-mu4nuzzs-4r9si5`. Attempt 2's agent returned no job id at all — only a companion background handle, `by36iouog`, with the `node … codex-companion.mjs` command line and a background output path. `codex wait by36iouog` answered `No job found for "by36iouog"` and exited 1. The skill's stated cause did not apply: the dispatch line carried `--cwd`, the forwarder passed it through (`--cwd "…/orko-smoke-codex/code"` is in the command it echoed), and the job had registered correctly as `task-mu4nzzaa-wdwhw7` under the code repository root.

**What I did:** did not take the literal branch. Taking it would have counted a dispatch that demonstrably ran as a delivery failure for a reason that was false, and would have spent the retry budget on a bookkeeping mismatch. Instead I read the job id out of the plugin's own job state directory, ran `codex wait` on it, and judged the delivery from the repository — which is the loop's stated principle. Recording the deviation here because it is a deviation. The fix the skill needs is a way to resolve the current task job for a workspace without depending on the forwarder's return text, and a `No job found` branch that distinguishes "wrong root" from "the id you were handed was never a job id."

### D4 — Three documents forbid writing `code/docs/testing/README.md` and the script's prompt orders it

The script-built `context/task-1.md`, line 3: "Boundaries: code/src/calc and code/tests only; docs/ records as the skill writes them. **docs/testing/README.md in the code repository is always inside them; the traceability row below goes there.**" And its closing instruction: "For every requirement row this task satisfies, add or update a row in docs/testing/README.md (in the code repository)…" `references/codex.md` backs it: "`docs/testing/README.md` is always inside the allowlist, because the task prompt tells every delivery to write it."

Against that: the intake boundaries recorded in the ledger are `code/src/calc and code/tests only`. `tasks.md` Global Constraints: "Do not edit `code/CONTRIBUTING.md`, `code/docs/`, `code/ARCHITECTURE.md`, or any file outside `code/src/calc` and `code/tests`. **What I did:** let it stand, on the most literal reading — the skill says the script owns every dispatch prompt and that this path is always in the allowlist, and `check delivery` raised no `diff-outside-allowlist`. Recorded it, and put it in the message to the human as the one thing the run did against the stated boundaries. ### D5 — A delivery decision has no ID, but the escalation procedure requires one

### D6 — `preflight` exempts only one of the three files the gate asks the human to edit

`references/record.md`: "The gate's expected edit is exempt because `preflight` re-records it." And: "So the gate asks a human for four fields in total: `status: accepted` and `approved_at` on the spec, `approved_by` on the spec review, and `approved_by` on the plan review."

### D7 — The trailer divergence is warned about but its consequence is not

`references/codex.md` → *Defaults*: "`init` records the executor, the Codex model plus effort overrides, the boundaries, and the attribution trailers in the ledger header. **What I did:** accepted the recorded pair, as the skill requires, and reported the divergence to the human. The skill should say whether a conductor must surface it and whether a resumed session's own attribution is recoverable.

`references/codex.md` → *The loop* step 4: "Read every `**Acceptance:**` line in `tasks.md` yourself before the first dispatch, and reject any that is not the repository's own test or lint runner: the script runs it as a shell command with your privileges." `references/build.md` repeats it at step 3.

`references/codex.md` → *The loop* step 3: "record the job id and the wall time from `startedAt` and `completedAt` **in your step summary**, and say the model is whatever `~/.codex/config.toml` sets when intake recorded no override."
