## Ambiguities and guesses

1. **`implementer-gap` or `implementer-multifile` for Task 2.** Task 2 is prose and touches three files (`cli.py`, `__init__.py`, a test). It had several small open points, not one: the return value, multi-character `--sep`, what counts as "blank", and empty slugs. The role guide gives "one small local gap" and "several files with integration concerns" as the two cases, and this task sat between them. I guessed `implementer-gap` because the files have no real integration concern, and it worked.
2. **Format for "record the assumption."** The `implementer-gap` bullet says "Record the assumption in the ledger" but gives no line shape. I used a `Ruling:` line so the assumption would reach Decided. A plain note wouldn't have.
3. **Decisions carried only in the dispatch.** The skill warns that a ruling carried only in `log --why` never reaches the report, but it says nothing about decisions written only into a dispatch prompt. I put two such decisions only in Task 2's dispatch: "blank means whitespace-only" and "tests patch stdin/stdout". Neither reached the report. That was my miss, but the skill could close the gap by saying that every decision in a dispatch must also be a ledger `Ruling:`.
4. **DONE_WITH_CONCERNS that is really a product decision.** The skill covers resuming over DONE_WITH_CONCERNS (no ledger line needed). It doesn't cover a concern that is a decision the plan leaves open, where the orchestrator rules and goes straight to review. I ruled and went to review.
5. **Overriding the plan's verbatim code with no spec.** Authority says "The plan is the controlling doc." SDD says the spec binds and the plan is only its argument, and the final reviewer's template says a reasonable user's expectation is a requirement. The skill's plan-conflict rule only spells out the branch where "the ruling keeps the plan → park". I read the other branch (the ruling departs from the plan → send the finding to the fixer) as implied, and ruled against Task 1's literal regex. The skill never says whether a ruling may override plan code when no spec exists.
6. **Final fixer returns NEEDS_CONTEXT.** The NEEDS_CONTEXT rules are written for per-task implementers. SDD allows exactly ONE final fix dispatch. I resumed the same fixer with `SendMessage`, treated that as the same dispatch, and logged nothing new. Neither file says whether that resume needs a `log` line, or whether a fresh re-dispatch would count as a second fix wave.
7. **Minors in the re-review's new-breakage section.** The skill tells me to record the final re-review's out-of-scope observations as deferred minors. SDD says new Critical or Important breakage joins the open findings. Neither covers Minor new breakage in the fix diff. I ledgered those as `Task final: minor (deferred)`.
8. **An out-of-scope observation that duplicates a ruling.** "Record the final re-review's out-of-scope observations" conflicts in spirit with "Don't restate … a ruling", although the second rule is scoped to `Follow-up:` lines. I didn't record it. That deviates from the literal instruction.
9. **Where the test and lint commands come from.** Finish step 1 says "the project's test and lint commands" but not where to find them. I used the project CLAUDE.md and the plan's Global Constraints.
10. **Re-running tests in finishing-a-development-branch.** That skill's Step 1 says to run the full suite. orko-sdd's verify step had just run it on the same clean HEAD, so I didn't run it again. Neither file says whether the verify run satisfies Step 1.
11. **Plan slug collisions.** A plan file named `plan.md` gives `feat/plan` and `.worktrees/plan`. That's a generic name, and the skill doesn't cover an existing branch or directory with the same name. It didn't happen in this run.

## Defects found

- **D1, the harness-refusal note is too narrow (Branch section).** The skill says the harness refuses a Bash call that "combines `cd` or `git -C` with git work". In this run, a call with neither was refused: it set a variable, ran `bash $S/task-brief …`, ran `git rev-parse HEAD`, then ran `python3 … log`. The refusal cited running `bash` on shell text that "cannot be shown not to run git". Fix: widen the note to cover any compound call that mixes a `bash <script>` or variable expansion with git, and tell the orchestrator to run each SDD script and each git command as its own call.
- **D2, deferred minors can't be retired, so the report shows stale lines.** Two report lines were wrong by the end of the run. The Task 1 minor "slugify drops non-ASCII" was fixed by the final wave. The Task 2 minor "no test pins the empty-slug ruling (`!!!` → empty output line)" describes behavior that superseding ruling #4 reversed. The report's hedge ("the final fix wave may have resolved the ones the final review marked must-fix") doesn't help, and the second line now contradicts Decided. I had to correct this in Recommended. Fix: add a ledger shape such as `Task <N>: minor resolved — <words>` or `minor (superseded by ruling)`, and have `report` drop the matching lines. At minimum, drop minors the final review marked must-fix once `Task final: complete` exists.
- **D3, the final-fixer NEEDS_CONTEXT or BLOCKED path isn't specified.** See ambiguity 6. SDD's "ONE fix dispatch" rule and the skill's NEEDS_CONTEXT logging rule don't cover the final fixer.
- **D4, Minor new breakage from the final re-review isn't routed.** See ambiguities 7 and 8. The skill routes out-of-scope observations but not Minor new breakage, and it doesn't say what to do with an observation that a ruling already covers.
- **D5, the boundary between `implementer-gap` and `implementer-multifile`, and the assumption format.** See ambiguities 1 and 2. Neither caused a failure, but both were guesses.

None of these stopped a step. D2 is the only one that produced output visibly wrong in the report oiler reads.
