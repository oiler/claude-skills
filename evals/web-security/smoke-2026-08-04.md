## Review produced

### Security review — `GET /reports/download`

Do not ship this. The route has two independently critical defects, either of which alone lets an unauthenticated attacker read arbitrary files from the server. "Internal tool" is not mitigation: the OWASP 2025 A01 threat model assumes an authenticated-but-hostile or credential-phished insider, and internal reporting tools hold exactly the data worth taking.

Findings are ordered by severity. OWASP category IDs are from the 2025 Top 10.

---

#### 1. SQL injection in the token lookup — CRITICAL (A05 Injection)

```python
db.execute(f"SELECT * FROM users WHERE token = '{request.args.get('token')}'")
```

The token is interpolated into the SQL string with an f-string. This is the exact anti-pattern the skill flags: *"No string concatenation or f-strings in SQL."*

This is not merely a data-exfiltration bug — it is a **complete authentication bypass**, because the only authorization check in the route is the truthiness of the returned row:

```
GET /reports/download?token=' OR '1'='1&file=report.pdf
```

resolves to `WHERE token = '' OR '1'='1'`, returns the first row in `users`, `if user:` passes, and the file is served. No valid credential is required at any point. Chained with finding #2, an anonymous attacker reads any file the app process can open.

The same input also supports UNION extraction of the whole `users` table (including everyone else's tokens), and on a driver with multi-statement execution enabled, destructive statements.

**Fix — parameterize:**

```python
row = db.execute(
    "SELECT id, org_id FROM users WHERE token_hash = ?", (token_hash,)
).fetchone()
```

(Placeholder style depends on your DB-API driver's `paramstyle`: `?` for sqlite3, `%s` for psycopg/MySQLdb, `:name` for SQLAlchemy `text()`. Never build the string yourself regardless of style.)

#### 2. Path traversal into `send_file` — CRITICAL (A01 Broken Access Control)

```python
filename = request.args.get('file')
return send_file(f'/var/reports/{filename}')
```

`filename` is attacker-controlled and interpolated straight into a filesystem path with no resolution or containment check. The skill's path-traversal reference calls out this precise shape ("passing user input directly to FileResponse", "trusting the path without resolution").

```
?file=../../etc/passwd
?file=../../proc/self/environ        → leaks env vars, incl. DB creds and SECRET_KEY
?file=../../var/www/app/settings.py  → leaks source and secrets
?file=../../home/app/.ssh/id_rsa
```

Anything the Flask process's UID can read is readable. Note the encoded and doubled variants (`%2e%2e%2f`, `....//`) all work too — which is why the fix must not be string filtering.

Also note: `filename` is never checked for `None`. `request.args.get('file')` with no `file` param yields `None`, and the f-string renders it as the literal string `"None"`, producing a path of `/var/reports/None` — a 404 in the best case, an unhandled exception surfaced to the client in the worst (see #8).

**Fix — resolve, then verify containment, per the skill's canonical defense pattern:**

```python
from pathlib import Path

REPORTS_DIR = Path("/var/reports").resolve()

target = (REPORTS_DIR / filename).resolve()
if not target.is_relative_to(REPORTS_DIR) or not target.is_file():
    abort(404)
return send_file(target)
```

Three rules from the reference apply here: normalization must happen at the OS level (`resolve()`), never by stripping `../`; the check must happen **before** the file is opened; and `os.path.basename()` is not a substitute.

Two Flask-specific notes the reference does not cover but that matter for this route:

- `send_from_directory("/var/reports", filename)` performs the safe-join internally (Werkzeug's `secure_join`) and is the idiomatic Flask fix. It is a legitimate one-line alternative to the manual pattern above. Prefer it, and keep the `.resolve()` + `is_relative_to()` pattern only if you need the path object for other checks.
- Prefer serving by **report ID**, not by filename, and looking the real path up from the database. That eliminates the traversal surface entirely rather than defending it — the same reasoning the skill applies to include-path allowlisting.

#### 3. No authorization — any valid token reads every report — HIGH (A01 Broken Access Control / IDOR)

Even with #1 and #2 fixed, the route only asks *"does this token belong to some user?"* It never asks *"is this user allowed to read this specific report?"* Every authenticated user can read every file in `/var/reports`, including other teams' and other customers' reports, simply by guessing or enumerating filenames.

This is the IDOR pattern the skill's auth reference names directly: *"Always verify the requesting user has access to the specific resource, not just the resource type."* The checklist entry is *"Object-level access control (not just role checks)."*

**Fix — scope the lookup to the requesting user, and let a missing-or-unauthorized report produce the same 404:**

```python
report = db.execute(
    "SELECT stored_path FROM reports WHERE id = ? AND org_id = ?",
    (report_id, user["org_id"]),
).fetchone()
if report is None:
    abort(404)   # 404, not 403 — a 403 confirms the report exists
```

Returning 403 on an existing-but-forbidden report is itself an information leak (it confirms which report IDs are real). The current code's `return 'nope', 403` has that problem in addition to being unhelpfully terse.

---

#### 4. Credential passed in the query string — HIGH (A07 Authentication Failures)

`?token=...` puts a long-lived bearer credential into the URL. The skill states the rule flatly: *"Never send API keys in query parameters (they get logged in URLs, referrers, proxy logs)"*, and lists *"Accepting tokens from query parameters (logged in URLs, referrers, proxies)"* among JWT anti-patterns — the reasoning is identical for opaque tokens.

Concretely, this token lands in: the web server's access log, any reverse proxy or load-balancer log, APM/observability traces, browser history, and the `Referer` header of any outbound link on a subsequently rendered page. Every one of those is a lower-security store than your user database, and each retains the credential long after the request.

**Fix:** move it to `Authorization: Bearer <token>`, or — for a browser-facing download in an internal tool — use the session cookie you already have, with `HttpOnly`, `Secure`, and `SameSite=Lax` set:

```python
app.config.update(
    SESSION_COOKIE_SECURE=True,
    SESSION_COOKIE_HTTPONLY=True,
    SESSION_COOKIE_SAMESITE="Lax",
)
```

Because the download is a `GET` with no side effects, no CSRF token is required here — but if you later add a POST that generates or deletes reports, it needs one. Flask has no built-in CSRF protection (unlike Django); use Flask-WTF.

---

#### 5. Token appears to be stored and compared in plaintext, with no expiry — HIGH (A04 Cryptographic Failures)

`WHERE token = '<raw value>'` implies the raw bearer token is stored verbatim in the `users` table. A token is a credential; a database read (via #1's injection, a backup, a stray log line, or a support query) hands the attacker working credentials for every user at once. The skill's own principle — "use hashed or tokenized references when the original value isn't needed" — applies directly, and its password guidance is the same shape: never store the presented secret itself.

Three sub-issues:

- **No hashing at rest.** Store `sha256(token)` and look up by hash. (Unlike a password, a high-entropy random token doesn't need a slow KDF — plain SHA-256 is correct and fast here. Use bcrypt/argon2 only for human-chosen secrets.)
- **No expiry.** There is no `expires_at` in the query. A token minted a year ago still works, and there is no revocation path. The skill's JWT guidance — short-lived credentials, revocation via a tracked ID — is the same requirement in a non-JWT form.
- **One token per user, on the `users` row.** Rotating it logs the user out everywhere and there's no way to scope or revoke a single client. Move tokens to their own table.

Timing-safe comparison is worth a note: hash-column lookup is a database index comparison, not a byte-by-byte compare of a secret in Python, so it's acceptable. If you ever compare a token in application code, use `hmac.compare_digest`, not `==`.

---

#### 6. No rate limiting — MEDIUM (A07 Authentication Failures)

The skill's rule: *"All public-facing endpoints should have rate limits"*, and the checklist requires *"Rate limiting on public endpoints."* This route has none, so an attacker can brute-force tokens and enumerate report filenames as fast as the server will answer. The endpoint doubles as an authentication endpoint (the token check *is* the login), which is the category the skill says to throttle hardest.

**Fix** (Flask equivalent of the skill's slowapi/django-ratelimit patterns):

```python
from flask_limiter import Limiter
from flask_limiter.util import get_remote_address

limiter = Limiter(get_remote_address, app=app)

@app.route("/reports/download")
@limiter.limit("30/minute")
def download_report():
    ...
```

Distinguish the two limits: a generous per-user limit on successful downloads, and a strict per-IP limit on *failed* token checks.

---

#### 7. `SELECT *` over the users table — MEDIUM (A04 / data minimization)

The route needs, at most, the user's ID and org. `SELECT *` pulls every column — email, phone, password hash, the token itself, whatever PII the table holds — into request scope, where it can end up in a traceback frame, an APM payload, or a debug log. The skill's data-handling reference is explicit about selecting only needed columns and excluding sensitive ones.

**Fix:** name the columns you need. `SELECT id, org_id FROM users WHERE token_hash = ?`.

---

#### 8. No error handling and no audit logging — MEDIUM (A10 Mishandling of Exceptional Conditions / A09 Logging Failures)

- **Errors.** `send_file` on a missing path raises `NotFound`; other failures raise `OSError`. If `FLASK_DEBUG` is on — a real risk for an "internal tool" — the interactive debugger returns a traceback containing source, local variables, and the full filesystem path, and (with the PIN defeated or disabled) a remote code-execution console. The skill's core principle: *"Fail securely — errors must not expose system details."* Confirm `debug=False` in whatever runs this in production, and register a handler that returns a generic message while logging the detail server-side.
- **Logging.** A sensitive-report download endpoint emits no audit record. There is no way to answer "who downloaded which report, when" after an incident — A09 in the 2025 list. Log `user_id`, `report_id`, timestamp, and outcome. Per the skill's logging rules, log **IDs, not PII**, and never log the token value itself.

---

#### Lower-priority notes

- **Response headers.** Reports served from an application route should carry `X-Content-Type-Options: nosniff` and an explicit `Content-Disposition: attachment` so a browser never renders a report inline (an HTML- or SVG-bodied report file becomes stored XSS on your own origin otherwise). `send_file(..., as_attachment=True)` handles the latter. The skill's checklist also wants CSP and HSTS set app-wide.
- **`/var/reports` is outside the web root — good.** Keep it that way. The skill notes that containment inside a base directory prevents traversal but not *exposure*; if that directory were ever mapped into a vhost root, every report becomes URL-reachable regardless of this route's checks.

#### Rewritten route

```python
import hashlib
import hmac
import logging
from pathlib import Path

from flask import abort, request, send_from_directory
from flask_limiter import Limiter
from flask_limiter.util import get_remote_address

logger = logging.getLogger(__name__)
limiter = Limiter(get_remote_address, app=app)

REPORTS_DIR = Path("/var/reports").resolve()


def _current_user():
    """Resolve the bearer token from the Authorization header to a user row."""
    header = request.headers.get("Authorization", "")
    scheme, _, token = header.partition(" ")
    if not hmac.compare_digest(scheme, "Bearer") or not token:
        return None

    token_hash = hashlib.sha256(token.encode()).hexdigest()
    return db.execute(
        "SELECT u.id, u.org_id FROM api_tokens t "
        "JOIN users u ON u.id = t.user_id "
        "WHERE t.token_hash = ? AND t.revoked_at IS NULL AND t.expires_at > CURRENT_TIMESTAMP",
        (token_hash,),
    ).fetchone()


@app.route("/reports/<int:report_id>/download")
@limiter.limit("30/minute")
def download_report(report_id: int):
    user = _current_user()
    if user is None:
        abort(401)

    # Object-level authorization: the report must belong to the caller's org.
    report = db.execute(
        "SELECT stored_name FROM reports WHERE id = ? AND org_id = ?",
        (report_id, user["org_id"]),
    ).fetchone()
    if report is None:
        abort(404)  # 404 rather than 403 — do not confirm the report exists

    # Defense in depth: stored_name is app-generated, but verify containment anyway.
    target = (REPORTS_DIR / report["stored_name"]).resolve()
    if not target.is_relative_to(REPORTS_DIR) or not target.is_file():
        logger.error("report %s missing or outside base dir", report_id)
        abort(404)

    logger.info("report_download user=%s report=%s", user["id"], report_id)

    response = send_from_directory(
        REPORTS_DIR, target.name, as_attachment=True, max_age=0
    )
    response.headers["X-Content-Type-Options"] = "nosniff"
    return response
```

Changes from the original: report identified by ID rather than filename (removes the traversal surface at its root); parameterized query; token moved out of the URL, hashed at rest, expiring and revocable; object-level authorization scoped to the caller's org; rate limit; audit log with IDs only; containment check retained as defense in depth; attachment disposition and `nosniff`.

Before shipping, run `bandit -r .` over the app — it flags the f-string-into-`execute` pattern statically, which would have caught finding #1 in CI.

## Ambiguities and guesses

Every place the skill left me uncertain, including small ones.

1. **Flask is in the description but has no section anywhere in the skill.** The frontmatter description promises coverage for "WordPress, Laravel, Django, Flask, FastAPI, or Plotly Dash", but SKILL.md line 12 says the skill covers "WordPress (PHP), Laravel (PHP), Django (Python), FastAPI (Python), and Plotly Dash (Python/Flask)" — Flask only as a parenthetical of Dash. A grep across all 14 files confirms it: every Flask code sample lives under a "Plotly Dash" heading. The task I was handed is a **bare Flask route**, the single framework the description advertises and the body does not have a section for. I guessed that the Dash examples transfer (they mostly do, since Dash is Flask), but I had to make that call myself, and it fails for anything Dash-specific — e.g. `path-traversal.md`'s Dash snippet ends in `dcc.send_file`, which does not exist in bare Flask. **This is the single biggest gap the run exposed.**

2. **`send_from_directory` is never mentioned.** Flask/Werkzeug's built-in safe-join helper is the idiomatic one-line fix for finding #2, and it appears nowhere in the skill. I supplied it from my own knowledge. A reader following only the skill would hand-roll the pathlib check — correct, but more code and more room to get wrong than the framework primitive. Same class of omission as #1.

3. **No output format for a security review.** The skill's top trigger phrase is "security review", but nothing specifies what a review should look like: no severity scale, no ordering rule, no template, no statement of whether to emit patched code or prose. I invented Critical/High/Medium, ordered by severity, labeled with OWASP IDs, and chose to include a rewritten route. Another run of this skill could produce a structurally different deliverable from identical input — that is a determinism gap for the skill's headline use case.

4. **Two overlapping code-review checklists, no stated precedence.** SKILL.md has "Code Review Quick Checklist" (prose, 12 groups); `security-testing.md` has "Code Review Checklist" (checkboxes, 8 groups). They are near-duplicates, but not identical — LIKE-wildcard escaping, object-level access control, and `.env in .gitignore` appear only in the reference; "No `shell=True` with user input" and the dependency line appear only in SKILL.md. I ran both to be safe. Which is canonical is unstated.

5. **No guidance on opaque bearer tokens.** The routing table's closest row is "Sessions, cookies, JWT tokens", which lands on `session-cookie-jwt.md` — but that file covers cookies and JWTs only. This code uses a random opaque token in a database column, which is neither. Everything in finding #5 (hash the token at rest, `expires_at`, revocation, `hmac.compare_digest`, SHA-256 rather than bcrypt because the secret is high-entropy) I brought from outside the skill, guided only by the general "use hashed or tokenized references" line in `secure-data-handling.md`. Given how common DB-backed API tokens are in Flask/FastAPI, this feels like a real content gap rather than an edge case.

6. **Rate limiting routed only through an "API" heading.** The routing table's rate-limiting row is "REST APIs, rate limiting, tokens, SSRF" and `api-security.md` opens with "All public-facing endpoints". This route is a browser-facing HTML-ish download, not a REST API. I judged the guidance applies and used it, but a more literal reader could reasonably decide the API reference doesn't cover their non-API route and skip finding #6 entirely. The router's row label under-sells the file's scope.

7. **Timing-safe comparison is named but never explained.** `security-testing.md` says to test password-reset flows for "timing attacks", but no reference in the skill explains constant-time comparison or names `hmac.compare_digest`. I supplied the mechanism. A reader following the skill knows to *test* for the flaw without being told how to *fix* it.

8. **A factual wobble in `path-traversal.md`'s last anti-pattern.** The bullet reads: *"Forgetting that `realpath()` / `resolve()` require the path to exist."* That is true of PHP's `realpath()` (which returns `false`, as the file correctly explains earlier) but **not** of Python's `Path.resolve()`, which defaults to `strict=False` in 3.6+ and resolves non-existent paths without raising. Lumping the two under one bullet could lead a Python reader to add unnecessary existence-check gymnastics, or worse, to assume `resolve()` will raise on a traversal target that doesn't exist and therefore skip the `is_relative_to()` check. Small, but it's a correctness issue in the one reference that mattered most to this task.

9. **Severity language is absent from the skill, so it's all mine.** The skill never says which findings are ship-blockers. "Critical" for #1 and #2 versus "Medium" for #6 and #7 is my judgment. Related: the skill offers nothing on *how to tell the user to prioritize* — for a pre-ship review, "don't ship this" versus "ship with follow-ups" is the most consequential sentence in the deliverable, and no guidance exists for drawing that line.

10. **CSRF applicability took a beat to resolve.** The routing table sends "forms, permissions, CSRF" to `authentication-csrf.md`, whose CSRF section is entirely about POST/state-changing operations. This route is a `GET`. I concluded no CSRF token is needed and said so explicitly (with a forward-looking note about a future POST), but the skill never states the "GET with no side effects needs no CSRF token" rule directly — I inferred it from the section's framing. Minor, but a less-confident reader might have raised a spurious CSRF finding to be safe.

## Verdict

**Yes — the skill materially improved the review, but on breadth and consistency rather than on the headline vulnerabilities.**

What it added over a bare review:

- **Forced breadth.** The Code Review Quick Checklist made me sweep dimensions the snippet doesn't visibly contain — rate limiting, audit logging, response headers, data minimization. Findings #4, #6, #7 and both lower-priority notes came out of that sweep. Working bare on a 7-line snippet, the gravitational pull is to stop after the two critical bugs; the checklist is what pushed past them.
- **A specific, correct fix pattern.** `path-traversal.md` supplied the exact canonical defense (resolve at the OS level, verify containment, check *before* opening) along with the bypasses that defeat naive fixes (`....//`, `%2e%2e%2f`, double-encoding) and the trailing-separator subtlety in the pre-3.9 idiom. That's better than the from-memory version I'd have written.
- **A flat, quotable rule for #4.** "Never send API keys in query parameters" stated as a rule, with the reason (URLs, referrers, proxy logs), turns a hedge-able observation into a firm finding.
- **Consistent labeling.** The OWASP 2025 map gave every finding a category ID without my having to recall the 2025 renumbering (A05 Injection, A10 Mishandling of Exceptional Conditions).

What it did not add: the two critical findings themselves. Any competent reviewer sees the f-string-in-SQL and the unvalidated path immediately. The skill's value is in what comes *after* the obvious two.

Where it fell short for this specific task: **the framework match was the weakest part of the run.** A bare Flask route is advertised in the description and unsectioned in the body, and the two most useful Flask-specific answers — `send_from_directory` for #2 and Flask-Limiter for #6 — came from me, not the skill. The largest content gap is DB-backed opaque bearer tokens (#5), which is the dominant auth pattern in exactly the Flask/FastAPI space the skill claims.

Two changes would have the highest leverage on the next run of this task:

1. Give Flask its own first-class treatment — either real sections alongside Django/FastAPI, or an explicit "Flask: see the Dash examples, with these substitutions" note plus the Flask-specific primitives (`send_from_directory`, Flask-Limiter, Flask-WTF for CSRF, `app.config` cookie flags). Right now the description writes a check the body doesn't cash.
2. Add a short "how to deliver a security review" section — severity scale, ordering, ship/don't-ship call, whether to emit patched code. It's the skill's headline trigger and the one thing it doesn't specify.

Net: a bare review would have caught roughly the first three findings well and gestured at the rest. The skill-guided review caught eight with consistent severities, correct fix patterns, and OWASP labels. That's a real improvement, achieved despite the framework gap rather than because the framework coverage was there.
